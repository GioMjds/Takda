# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Source of truth.** Root `README.md` is canonical for product/domain. Backend-specific architecture lives in `api/ARCHITECTURE.md` (data layers, DTOs, exceptions, barrel layout). This file is the API-only entry point and adds the patterns that are not in either of those -- stack quirks, runtime wiring, module bootstrap, and conventions that span multiple modules.

## Commands

All commands run from `api/`.

| Task                   | Command                                                              |
| ---------------------- | -------------------------------------------------------------------- |
| Install                | `pnpm install`                                                       |
| Dev server (swc watch) | `pnpm dev`                                                           |
| Production start       | `pnpm build` then `pnpm start:prod`                                  |
| Lint (with --fix)      | `pnpm lint`                                                          |
| Unit tests             | `pnpm test`                                                          |
| Single unit test       | `pnpm test -- path/to/file.spec.ts`                                  |
| Watch tests            | `pnpm test:watch`                                                    |
| Coverage               | `pnpm test:cov`                                                      |
| E2E tests              | `pnpm test:e2e`                                                      |
| Prisma generate        | `pnpm prisma generate`                                               |
| Regenerate barrels     | `pnpm barrels`                                                       |
| Nest REPL              | `pnpm start -- --entryFile repl` or run `node dist/repl` after build |

`pnpm dev` uses `nest start -b swc` (SWC builder, not the default tsc). The SWC build is faster but skips type checking; rely on `tsc --noEmit` (implicit via editor/IDE) for type errors.

│   ├── pipes/                     # ZodValidationPipe

Path alias: `@/*` -> `./src/*` (set in `tsconfig.json`). Import paths:

- `@/modules` -- feature module barrel
- `@/common` -- cross-cutting namespace (`@/common/exceptions`, `@/common/guards`, ...)
- `@/config` -- `ENV` object
- `@/shared` -- `SharedModule`

Generated Prisma client is excluded from `tsconfig.json` (`exclude: ["node_modules", "dist", "src/generated"]`); regenerate with `pnpm prisma generate` after schema changes.

## Bootstrap (`src/main.ts`)

- **CORS** is hard-coded for the dev machine IPv4 (`networkInterfaces()` scan) plus `localhost:3000`. Production uses the same origin list unless overridden -- plan to externalise `CORS_ORIGINS` before deploying.
- **Cookie parser** is enabled (`cookieParser()`); `JwtAuthGuard` accepts the JWT from either the `Authorization: Bearer` header or the `access_token` cookie.
- **URI versioning**: every route is prefixed with `/v1` automatically. E2E tests pin to `v1` (`/v1/auth/...`).
- **Global `ValidationPipe`** runs with `whitelist: true`, `forbidNonWhitelisted: true`, `transform: true` -- extra body fields are rejected, DTOs are stripped to schema fields.
- Logger levels are gated by `NODE_ENV` (`production` -> error/warn/log only).

## Environment (`src/config/env.ts`)

Process env is parsed through a single Zod schema in `src/config/env.ts`. The exported `ENV` object is the only typed env accessor (`import { ENV } from '@/config'`). Adding a new env var: add it to the schema (with `.default()` if optional), then read via `ENV.<KEY>` or `config.get<string>(ENV.<KEY>)` in Nest providers.

Notable keys: `DATABASE_URL`, `JWT_SECRET` (min 32 chars), `JWT_ACCESS_TTL_SECONDS`, `JWT_REFRESH_TTL_SECONDS`, `SMTP_*`, `SMS_*` (`semaphore` | `twilio`), `RATE_LIMIT_LOGIN_MAX` / `RATE_LIMIT_LOGIN_WINDOW_MS`, `IDEMPOTENCY_CACHE_TTL_MS`, `THROTTLE_TTL` / `THROTTLE_LIMIT`, `FRONTEND_URL`, `MOBILE_APP_SCHEME`.

## Layered data access

`Controller -> Service -> Repository -> PrismaService -> Postgres`. Lower layers must not depend on upper layers. See `ARCHITECTURE.md` for the full pattern; the important API-specific rules:

- **Repositories throw `DomainException` subclasses** when Prisma signals missing rows (`P2025` translated to `UserNotFoundException`, etc.) -- the `HttpExceptionFilter` maps the exception class to an HTTP status. Don't rethrow plain `Error`s from repositories.
- **Repositories return domain types, not Prisma rows.** Use `toUserPublic(row)` mappers; never leak `password` or other hashed fields up the stack. Routes that need the password hash (e.g. login) get a separate `*WithPassword` return type from a dedicated repository method.
- **Soft-delete / archive filters live in the repository**, not the service. Repos default to `deletedAt: null` and `archivedAt: null`; callers opt in via `{ includeDeleted: true, includeArchived: true }`.
- **Transactions** use `prisma.$transaction(async (tx) => ...)` inside the repository when an operation spans multiple tables (e.g. `createBusinessOwner` creates `Tenant` + `User` in one tx).

## Validation (Zod only)

- All request DTOs are Zod schemas in `dto/<action>-<entity>.schema.ts`, exporting both the schema and `z.infer`-typed DTO.
- Pipe via `new ZodValidationPipe(<Schema>)` on the controller method or `@Query(...)`.
- Don't mix `class-validator` with Zod in the same DTO -- class-validator decorators are not used in this codebase (the `class-validator` package is only in deps because some libraries transitively pull it in).
- Query-string booleans: use `z.union([z.literal('true'), z.literal('false')]).transform(...)` -- see `find-users-query.schema.ts`.
- Coerce numbers from query strings: `z.coerce.number().int().min(0).max(...)`.

## Authentication & authorisation

- **JWT** (`@nestjs/jwt`) -- access token is short-lived (`JWT_ACCESS_TTL_SECONDS`, default 900s); refresh token is long-lived (`JWT_REFRESH_TTL_SECONDS`, default 30d) and tracked as a row in `RefreshToken` with `tokenHash`, `revokedAt`, `expiresAt`. Logout sets `revokedAt`; `/auth/refresh` revokes the old row and issues a new pair.
- **`JwtAuthGuard`** (`src/common/guards/jwt-auth.guard.ts`) accepts JWT from `Authorization: Bearer` header or `access_token` cookie. Throws `UNAUTHORIZED` (missing) or `INVALID_TOKEN` (verify failed).
- **`@Public()`** decorator skips the JWT check for opt-in routes (login, register, refresh, forgot/reset password, public health).
- **`@Roles(UserRole.X, ...)`** + `RolesGuard` enforces RBAC. Roles live on the JWT payload (`role`) and are sourced from Prisma's `UserRole` enum.
- **`@CurrentUser()`** returns the `CurrentUserPayload` (`userId`, `tenantId`, `email`, `role`). For request-scoped tenant-aware access use `TenantContextService` (REQUEST-scoped; throws `TenantRequiredException` when `tenantId` is missing).
- **Rate limiting**: global `ThrottlerModule` (env-configured) + per-route `@RateLimit({ windowMs, max })` (`src/modules/auth/rate-limit/`) backed by an in-process token bucket. Add the `RateLimitGuard` to controllers that need it (currently only `AuthController`).

## Audit logging

`AuditService` (`src/modules/users/audit.service.ts`, reusable across modules -- instantiate per module or import the one from `UsersModule`) writes append-only rows to `AuditLog` via `prisma.auditLog.create`. Call it after a successful business operation:

```ts
await this.audit.logAction({
  action: 'USER_CREATED',
  entity: 'User',
  entityId: user.id,
  actorUserId: actor.userId,
  payload: { email: user.email, role: user.role },
});
```

Failures bubble -- `AuditService` logs the error then rethrows.

## Eventing

`EventEmitterModule` is global with `wildcard: false`, `delimiter: '.'`, `maxListeners: 10`. Mail listeners (`src/modules/auth/mail/mail.listener.ts`) subscribe to `mail.invite.*` / `mail.password_reset.*` events and dispatch through the `MailService` interface -- the `nodemailer` impl is the only production binding, but the interface lets unit tests inject a fake.

## Idempotency

`@node-idempotency/nestjs` is wired in the root module with in-memory storage. Apply `@Idempotent()` on write controllers to make POSTs safe to retry.

## Hardening

- `helmet`, `compression`, global `ThrottlerGuard` are all wired in `app.module.ts` / `main.ts`.
- Global `ValidationPipe` rejects unknown body fields (`forbidNonWhitelisted: true`).

## WebSockets

`@nestjs/platform-socket.io` + `socket.io`. Gateways live next to their feature module. Errors go through `WsExceptionFilter` (`src/common/filters/ws-exception.filter.ts`) which emits an `exception` event with `{ status: 'error', code, message }` to the offending client.

## Prisma

- Driver-adapter pattern via `@prisma/adapter-pg` (a `pg.Pool` is built from `DATABASE_URL` and handed to `PrismaPg`). Connection lifecycle (`$connect` / `$disconnect`) is managed by `PrismaService` lifecycle hooks.
- The `PrismaModule` is `@Global()`, so `PrismaService` is injectable anywhere without re-importing.
- Schema lives at `api/prisma/schema.prisma`. After edits: `pnpm prisma generate`.
- The schema currently models a clinic/doctor workflow (`User`, `Patient`, `Doctor`, `Appointment`, ...). It is converging toward the README's queue/booking vision -- when writing code, use the target domain terms in comments and identifiers only where they map cleanly to existing schema fields. See `README.md` §6 for the target terms (Tenant, Business, Service, Slot, Booking, Walk-in, Reminder, Queue position).

## Barrels

- **Auto-generated barrels** (`scripts/generate-barrels.mjs`, run via `pnpm barrels`) live in every folder. They begin with the comment `// Auto-generated barrel. Do not edit by hand.` -- don't hand-edit them.
- **Hand-written barrel:** `src/modules/index.ts` is intentionally hand-written (the comment in the file explains why). When you add a new feature module, export its module class from there manually.
- Sub-path namespaces (`dto`, `mail`, `rate-limit`) are accessed by importing the sub-barrel directly: `import { LoginDto } from '@/modules/auth/dto'` -- the top-level `@/modules` barrel does not re-export them.

## Testing

- **Unit tests** live next to source: `src/**/*.spec.ts`. Run with `pnpm test` (Jest, `rootDir: src`, `testRegex: .*\.spec\.ts$`).
- **E2E tests** live in `api/test/` and use `*.e2e-spec.ts`. They boot the full `AppModule` against a real Postgres (or the docker-compose dev DB). Run with `pnpm test:e2e` (uses `test/jest-e2e.json`, sets `setGlobalPrefix('v1')` so request URLs are `/v1/...`).
- Mock Redis, SMS, mail, and the DB in unit tests. Real DB access is reserved for E2E.

## Domain exceptions

All domain errors extend `DomainException` (`src/common/exceptions/domain.exception.ts`):

- `NotFoundException` (HTTP 404) -- base; `UserNotFoundException` extends it
- `ConflictException` (HTTP 409)
- `UnauthorizedException` (HTTP 401)
- `InvalidStateException` (HTTP 400)
- `ValidationException` (HTTP 422) -- carries `errors: ValidationError[]`
- `ForbiddenException` (HTTP 403)

`HttpExceptionFilter` handles `HttpException`, the listed subclasses, and falls back to `DomainException` -> HTTP 400 / `Error` -> HTTP 500. WebSocket errors are handled separately by `WsExceptionFilter`.

## ESLint notes

- Flat config (`eslint.config.mjs`); TypeScript-aware rules. Several `@typescript-eslint/no-unsafe-*` rules are turned **off** in the config -- don't re-enable them without a deliberate sweep. Prettier formatting conflicts are suppressed.
- `lint` runs with `--fix`. Don't rely on it to format freshly-written code -- write it Prettier-clean from the start.

## Definition of done (API-specific)

- `pnpm lint` clean
- `pnpm test` passes (add a unit test for any new behavior)
- `pnpm prisma generate` succeeds if `schema.prisma` changed
- `pnpm barrels` succeeds if files were added/moved
- New module is exported from `src/modules/index.ts`
- New env vars go through the Zod schema in `src/config/env.ts`
- New endpoints route under `/v1/...` (URI versioning is automatic, but tests must hit the prefixed path)
